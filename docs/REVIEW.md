# Code Review: Kohonen Self-Organising Map

**Reviewer:** Benya Wang
**Subject:** `notebooks/kohonen.ipynb`
**Date:** 2026-08-24

---

## Summary

The implementation is correct in its broad strokes — the algorithm matches the
brief, and the author clearly understood it. The BMU search is already
vectorised, which shows the technique was known.

Two lines later, the neighbourhood update is a nested Python loop over every
node. That single choice makes the notebook's own second example take about
five minutes instead of about two seconds, and it is the largest finding here.

Beneath that sit five correctness defects, one of which is an unguarded
division by zero on small grids. None would be caught today, because there are
no tests.

Everything below is reproducible from this repository. Every figure comes from
`benchmarks/results/comparison.json`, generated by `benchmarks/compare.py`.

---

## Observations

### Efficiency

The BMU search on line 4 of `train` is already vectorised:

```python
bmu = np.argmin(np.sum((weights - vt) ** 2, axis=2))
```

The weight update immediately below it is not:

```python
for x in range(width):
    for y in range(height):
        di = np.sqrt(((x - bmu_x) ** 2) + ((y - bmu_y) ** 2))
        theta_t = np.exp(-(di ** 2) / (2 * (sigma_t ** 2)))
        weights[x, y] += alpha_t * theta_t * (vt - weights[x, y])
```

For the 100×100 example this executes 100 million Python-level iterations, each
allocating NumPy temporaries to update a three-element vector.

The measured cost is the tell:

| Grid | Original, per weight update |
|---|---|
| 10×10 | 3151 ns |
| 30×30 | 3101 ns |
| 100×100 | 3091 ns |

**The cost per node is flat across a hundredfold change in grid size.** That is
not algorithmic cost — it is per-node Python interpreter overhead, invariant to
the work being done. The fix is not a better algorithm; it is removing the
interpreter from the inner loop.

### Correctness

1. **`lambda = n_iterations / log(sigma_0)` divides by zero** when
   `max(width, height) == 2`, because `sigma_0 == 1` and `log(1) == 0`. On a
   1×1 grid `lambda` is *negative*, so the neighbourhood radius grows instead of
   decaying — the map would actively un-organise. Unguarded.
2. **The radius is computed and then never used as a radius.** The brief's step
   4 selects nodes *within* the neighbourhood; the code applies the Gaussian to
   all nodes unconditionally. Defensible mathematically, but undocumented, and
   it is why the update is O(W·H) per sample rather than O(σt²).
3. **`t` is the epoch index, not the iteration counter.** With 10 samples and
   100 epochs, decay advances once per 10 weight updates. The brief is ambiguous
   here — but the choice is silent, so a reader cannot tell whether it was
   deliberate.
4. **Input dimensionality is hardcoded to 3.** The brief states that a
   10-element input vector implies 10 weights per node; this implementation
   accepts RGB and nothing else.
5. **No seed.** `np.random.random` draws from global state, so no run is
   reproducible. Fatal for anything that ships.

### Structure

No package, tests, type hints, docstrings, or input validation. A single
20-line function performs initialisation, scheduling, and training; the
`__main__` block additionally generates data and writes PNGs, so the algorithm
cannot be exercised without also doing file I/O. Greek identifiers (`σ0`, `αt`)
are unsearchable and fragile on non-UTF-8 toolchains.

## The Five Recommendations

Ordered by business impact rather than technical novelty.

| # | Recommendation | Evidence |
|---|---|---|
| **1** | **Vectorise the neighbourhood update.** Replace the nested grid loop with broadcast operations over a coordinate grid built once per run. | 161× at 100×100; deviation 2.220e-16 |
| **2** | **Make it correct and reproducible.** Inject the seed, guard the degenerate radius, validate inputs, infer dimensionality from data. | Fixes 5 defects incl. a division by zero |
| **3** | **Separate the algorithm from its I/O and configuration.** A typed `SOM` with `fit`/`predict`; decay as an injectable policy; no plotting inside the trainer. | Enables testing, reuse, non-RGB data |
| **4** | **Test it like it ships.** Keep the original as an executable oracle; add property-based tests for the invariants. | 103 tests, 100% coverage, CI on 3.10–3.14 |
| **5** | **Do not reinvent the wheel — but know when the wheel is wrong.** Benchmark against MiniSom; adopt its conventions where they win. | See the comparison below |

### On recommendation 1

The speed-up is not a fixed number — it **scales with grid size**, because what
is being removed is per-node interpreter overhead:

| Grid | Original | Vectorised | Speed-up |
|---|---|---|---|
| 10×10, 100 iterations | 0.315 s | 0.0133 s | **24×** |
| 30×30, 100 iterations | 2.791 s | 0.0299 s | **93×** |
| 100×100, 10 iterations | 3.091 s | 0.0192 s | **161×** |

Extrapolated, the notebook's own second example (100×100, 1000 iterations)
takes roughly **five minutes**; the vectorised equivalent takes about **two
seconds**.

### On recommendation 4

The distinguishing move: **`src/kohonen/_reference.py` retains the original
implementation**, and CI asserts the fast path matches it to `atol=1e-12`
across 38 parametrised cases — four grid shapes, three dimensionalities, three
seeds, plus the notebook's own configuration.

The worst observed deviation is **2.220e-16**, which is exactly
`np.finfo(np.float64).eps`. The optimisation is therefore *semantics
preserving*, not an approximation.

Most refactors delete the code they replace. Keeping it as an executable oracle
is what makes a rewrite of a numerical routine safe rather than merely
plausible. A test also asserts the oracle is never imported by shipped code.

### On recommendation 5

`scikit-learn` has no SOM, so MiniSom is the real comparator.

| Grid | Original | This library | MiniSom |
|---|---|---|---|
| 10×10 | 0.315 s | **0.0133 s** | 0.0181 s |
| 30×30 | 2.791 s | **0.0299 s** | 0.0421 s |
| 100×100 | 3.091 s | **0.0192 s** | 0.0294 s |

**This comparison needs a caveat, and the caveat matters more than the win.**
MiniSom is not running the same algorithm: it uses asymptotic decay
`1/(1+t/(T/2))` rather than the exponential decay this brief specifies. Raw
wall-clock across the two is therefore not a like-for-like measure. The
benchmark normalises on *weight updates performed* and records the algorithmic
difference in every MiniSom row of the output JSON.

Quantisation error tells the same story from the other side — identical between
the original and this library (0.1031 vs 0.1031, as the equivalence proof
requires), but different for MiniSom (0.1148). The libraries are solving
slightly different problems.

Where the wheel does win: **adopt scikit-learn's conventions.**
Hyperparameters in `__init__`, learned state as `weights_`, `fit` returning
`self`. This library follows all three without taking the dependency — a
200-line numerical package should not pull in scikit-learn's transitive tree to
borrow an interface.

## What I Did Not Do, And Why

This section is as important as the recommendations.

- **No GPU or numba backend.** At 100×100 the vectorised implementation
  finishes in about two seconds. Adding a CUDA path would be complexity the
  data does not justify. The threshold at which that changes is in
  [the ADR](adr/0001-productionisation.md).
- **No REST inference API.** A SOM is a batch training job, not an
  online-inference product. Building `/predict` for it would demonstrate
  familiarity with FastAPI and a misunderstanding of the workload.
- **No CLI or Docker image.** Both are straightforward; neither was the
  bottleneck. Time went into the equivalence proof instead, which is the thing
  that makes every other claim here trustworthy.
- **`somoclu` was not benchmarked.** The C++/OpenMP implementation would
  plausibly beat this one at large grid sizes, and that result would have been
  published had it run — but it does not build on Windows. The harness skips it
  gracefully. This is a gap in the comparison, not a favourable omission.
- **`radius_cutoff` is accepted but not yet consumed.** Restricting updates to
  a window around the BMU is a real optimisation, but it is an *approximation*,
  and shipping it without first measuring its deviation would contradict the
  standard the rest of this work is held to.
