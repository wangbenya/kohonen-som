A map that organises itself

What the algorithm does, where its specification contradicts itself, what the rewrite measured, and how to reuse the result.

Section 1

What a SOM is, and how this was built

Give it a pile of things it has never seen, with no instructions about what they are. It arranges them on a grid so that similar things end up near each other. Nobody defines “similar” — it works that out from the data.

Where it earns its keep

Customer segmentation
Segments emerge from behaviour instead of being defined upfront.
Fraud and anomaly detection
Anything landing far from the whole map is unlike what came before.
Document clustering
Organise a corpus by topic with no predefined taxonomy.
Equipment health
Sensors drifting to a new region signal a machine unlike its own history.

And where it is the wrong tool

  • With labels and a specific target, a supervised model wins comfortably.
  • It gives a smooth landscape, not tidy clusters — drawing boundaries is a separate judgement.
  • “It landed in this region” is a weak account for a regulator.

Two ideas behind the code

Don’t reinvent the wheel — but know which wheel

NumPy does the arithmetic; the API borrows scikit-learn’s conventions; MiniSom is the benchmark. A SOM was still written from scratch for one reason: this brief is prescriptive. It specifies a particular decay, which MiniSom does not implement — so MiniSom cannot answer it. When the spec is loose, take the library; when the spec is the point, implement it and benchmark against the library anyway.

Writing code is cheap now. Maintaining it is not.

An assistant produces a working SOM in seconds. That moves the value to what it cannot supply — what to keep, what to delete, what to prove — because the next person to touch this is a support team, a client’s engineers, or you in six months with no memory of the reasoning.

So the original implementation is kept rather than deleted, odd-looking decisions carry their reason beside them, the spec’s ambiguities are documented rather than quietly resolved, and the tempting-but-unjustified parts were left out. Code that cannot be safely changed by someone else is not finished.

Section 2

The brief, the code, and where they disagree

The notebook holds two things: a specification, and an implementation of it. Reviewing the code alone would miss the more interesting finding — the specification contradicts itself, and the code silently picks a side.

The contradiction

Step 4 of the brief says, in words:

“Any nodes found within this radius are deemed to be inside the BMU’s neighbourhood.”

That describes a circle: inside it you update, outside it you don’t. But the brief’s own influence formula has no circle in it —

What the words describe
if distance <= radius:
    update(node)      # hard edge
else:
    pass              # untouched
What the formula describes
theta = exp(-d**2 / (2 * sigma**2))
update(node, by=theta)
# every node, fading with distance,
# never exactly zero

The code follows the formula — the more standard Kohonen formulation. Sigma is not a wall; it is the width of a glow. With sigma = 5, distant nodes barely move:

Distance from winnerInfluenceEffect
01.000full update
5  (1σ)0.607strong
10 (2σ)0.135modest
15 (3σ)0.011about 1%
20 (4σ)0.0003negligible

Adding a cutoff does not correct the mathematics — it says “those nodes barely move, skip them and save the compute.” The cutoff is an optimisation; the smooth version is the definition.

t is the same story: the brief’s wording fits the pass-over-the-data reading the code took. So neither is a bug. The fair criticism is narrower — the code never records which reading it took, so a maintainer cannot tell whether the ambiguity was noticed or missed.

What is genuinely wrong

  1. Division by zero on small grids. lambda = n_iterations / log(sigma_0) is undefined when max(width, height) == 2 — sigma_0 is 1 and log(1) is 0. On a 1×1 grid it goes negative, so the neighbourhood grows instead of shrinking and the map actively un-organises.
  2. Dimensionality hardcoded to 3. The brief states plainly that a 10-element input means 10 weights per node. np.random.random((width, height, 3)) accepts colour and nothing else, directly contradicting it.
  3. No seed. Global random state, so no run is reproducible and no result can be audited or compared.

Beyond those: no tests, type hints, docstrings or validation. One function does initialisation, scheduling and training, and the entry point also generates data and writes PNGs — so the algorithm cannot be run without file I/O. The Greek identifiers (σ0, αt) are unsearchable and break on non-UTF-8 toolchains.

Answering the challenge

Could the code be made more efficient?

Yes — substantially, and provably without changing the result. There are four nested loops, but only the inner two can go: they walk the grid per sample and are pure interpreter overhead. The outer two are inherent to online SOM — vectorising across samples would silently turn this into batch SOM, which converges differently.

Removing the inner two gives a large speed-up that grows with grid size, deviating from the original by 2.220e-16 — one float64 epsilon.

Is it structured for other developers and for productionisation?

Not yet. It is one function returning a bare array, with no inference path at all — anyone wanting to map a new vector onto the trained grid must reimplement the best-matching-unit search themselves.

The rewrite splits training from inference behind a typed class (fit, predict, transform), moves hyperparameters into a validated frozen config, and takes plotting and dataset generation out of the algorithm entirely.

How would you approach productionising this?

By first rejecting the question’s implied shape. A SOM is a batch training job that emits an artefact, not a service. The reflex to containerise it and put an API in front answers a workload this is not.

Concretely, on Databricks — Azure ML is the same shape with different nouns:

1
A scheduled Workflow trains it
One task reads the feature table from Delta, runs SOM(...).fit(...), and logs TrainingConfig as MLflow params — one call, because the config is a frozen dataclass — plus quantisation error as a metric.
2
The trained map goes into Model Registry
A SOM is not a native MLflow flavour, so it is wrapped in a thin pyfunc model. That buys the normal machinery: a version number, Staging and Production stages, and lineage back to the run and the commit that produced it.
3
A second task scores in batch
Load models:/kohonen-som/Production, map each row to its best matching unit, write the assignments back to Delta. No endpoint and no always-on compute — a REST service would add a network hop and an availability commitment to something the caller does locally in microseconds.
4
Drift shows up in the metrics
There are no labels, so there is no accuracy number. Log quantisation and topographic error on every retrain and alert on the trend — the absolute value depends on the data’s scale and means little alone.

The wrapper is the only glue the registry needs:

class SOMModel(mlflow.pyfunc.PythonModel):
    def load_context(self, context):
        self.som = joblib.load(context.artifacts["som"])

    def predict(self, context, model_input):
        return self.som.predict(model_input.to_numpy())

mlflow.pyfunc.log_model(
    artifact_path="som",
    python_model=SOMModel(),
    artifacts={"som": local_path},
    registered_model_name="kohonen-som",
)

Distribution. The package is installed from a private index — Azure Artifacts or CodeArtifact — not public PyPI, so versions stay pinned, auditable, and inside the tenancy.

Scaling. Below roughly 1000×1000 nodes NumPy is enough. Above that, measure before reaching for a GPU.

Anything else relevant?

There is no way to verify any change to this code. Without tests, refactoring a numerical routine is guesswork — you cannot tell a speed-up from a subtle behavioural change.

So the original is kept as an executable oracle: _reference.py stays in the package and CI asserts the fast version matches it to 1e-12. Most rewrites delete the code they replace. Keeping it converts “it looks right” into a claim that holds up.

What it measured

Time per weight update
Logarithmic scale — the series differ by two orders of magnitude. Lower is better.
This chart is the whole argument

The original’s bar barely moves across a hundredfold change in grid size — its cost per node is constant, because that cost is the interpreter, not the arithmetic. The rewritten bar falls as the grid grows, as NumPy spreads fixed overhead across more elements. That is why the speed-up is not one number: it scales with the problem.

GridImplementationWall clock ns / updateQuantisation error
The caveat matters more than the win

MiniSom is not running the same algorithm — it uses asymptotic rather than exponential decay, so raw wall-clock is not like-for-like. The benchmark normalises on weight updates performed.

Quantisation error says the same from the other direction: identical between the original and the rewrite, as the equivalence proof requires — but different for MiniSom. They solve slightly different problems.

Section 4

Using it in another project

One runtime dependency: NumPy. It ships type information, so consumers get completion and type checking without a stub package.

Install
# Straight from the repository
uv add git+https://github.com/wangbenya/kohonen-som.git

# Or clone it to work on
git clone https://github.com/wangbenya/kohonen-som.git
cd kohonen-som
uv sync --extra dev

# Or build a wheel to hand to another team
uv build
pip install dist/kohonen_som-0.1.0-py3-none-any.whl
Train and use a map
import numpy as np
from kohonen import SOM, TrainingConfig

data = np.random.default_rng(0).random((100, 3))

som = SOM(10, 10, config=TrainingConfig(n_iterations=100, seed=42)).fit(data)

labels = som.predict(data)             # nearest node per sample
error  = som.quantisation_error(data)  # mean distance to that node
image  = som.weights_                  # (10, 10, 3) — plottable directly

Why the API looks familiar

Hyperparameters in the constructor, learned state with a trailing underscore, fit returning self — scikit-learn’s conventions, adopted deliberately without taking scikit-learn as a dependency. A small numerical package should not pull in a large transitive tree to borrow an interface. Anyone who has used scikit-learn already knows how to drive this.

Reproducibility is structural, not procedural
from dataclasses import asdict

config = TrainingConfig(n_iterations=100, seed=42)

mlflow.log_params(asdict(config))   # frozen dataclass — one call
mlflow.log_artifact("weights.npy")

# Given the config, the data version and the commit,
# the identical map is re-derivable.

The config is frozen and hashable for exactly this reason: no hand-maintained parameter dictionary to drift out of step with the code.

What a consumer can rely on

  • Deterministic output for a given seed, asserted by tests.
  • Any dimensionality, inferred at fit time — and small grids work, including the 1×1 and 2×2 cases that divided by zero before.
  • Clear failure — bad grids, empty arrays, NaN, inf and dimensionality mismatches raise on entry with a message naming the problem, instead of producing quiet nonsense.

What it deliberately does not do

No GPU backend, REST API, CLI or container. All straightforward; none was the bottleneck. The effort went into the equivalence proof — the thing that makes every other claim here trustworthy.
