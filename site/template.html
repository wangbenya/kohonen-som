Kohonen Self-Organising Map code review · benchmarks · explainer

Code review

The algorithm was right. The loop around it wasn’t.

The best-matching-unit search was already vectorised — so the technique was known. Two lines later, the weight update is a nested Python loop over every node on the grid. That one choice is the difference between five minutes and two seconds.

The finding

The BMU search on line four of train is already vectorised. The weight update immediately below it is not.

Original — ~3100 ns per node
for x in range(width):
    for y in range(height):
        di = np.sqrt(((x - bmu_x) ** 2)
                   + ((y - bmu_y) ** 2))
        theta_t = np.exp(-(di ** 2)
                  / (2 * (sigma_t ** 2)))
        weights[x, y] += alpha_t * theta_t \
                       * (vt - weights[x, y])
Vectorised — 19 ns per node
diff  = weights - sample
d2    = squared_distance_to(
            grid_x, grid_y, bmu_x, bmu_y)
theta = gaussian_influence(d2, sigma_t)

weights -= (alpha_t * theta)[..., None] * diff

For the 100×100 example the original executes roughly 100 million Python-level iterations, each allocating NumPy temporaries to update a three-element vector.

The cost per node is flat across a hundredfold change in grid size

3151 ns at 10×10. 3101 ns at 30×30. 3091 ns at 100×100. That is not algorithmic cost — it is per-node Python interpreter overhead, invariant to the work being done. The fix isn’t a better algorithm; it’s removing the interpreter from the inner loop.

Five correctness defects

  1. Division by zero on small grids. lambda = n_iterations / log(sigma_0) is undefined when max(width, height) == 2, because sigma_0 == 1 and log(1) == 0. On a 1×1 grid lambda goes negative, so the neighbourhood grows instead of decaying — the map actively un-organises.
  2. The radius is computed, then never used as a radius. The brief selects nodes within the neighbourhood; the code applies the Gaussian to all nodes unconditionally. Defensible, but undocumented.
  3. t is the epoch index, not the iteration counter. With 10 samples and 100 epochs, decay advances once per 10 weight updates. The brief is ambiguous — but the choice is silent.
  4. Dimensionality hardcoded to 3. The brief says a 10-element input implies 10 weights per node. This accepts RGB and nothing else.
  5. No seed. np.random.random draws from global state, so no run is reproducible.

Five recommendations

Ordered by business impact rather than technical novelty. The ordering is part of the recommendation.

1
Vectorise the neighbourhood update
Replace the nested grid loop with broadcast operations over a coordinate grid built once per run.
161× at 100×100 · deviation 2.220e-16
2
Make it correct and reproducible
Inject the seed, guard the degenerate radius, validate inputs, infer dimensionality from the data.
fixes 5 defects, including a division by zero
3
Separate the algorithm from its I/O and configuration
A typed SOM with fit/predict; decay as an injectable policy; no plotting inside the trainer.
enables testing, reuse, non-RGB data
4
Test it like it ships
Keep the original as an executable oracle; add property-based tests for the algorithm’s invariants.
103 tests · 100% coverage · CI on Python 3.10–3.14
5
Don’t reinvent the wheel — but know when the wheel is wrong
Benchmark against MiniSom; adopt scikit-learn’s conventions without taking the dependency.
see the Benchmarks tab

The move that makes recommendation 4 work

src/kohonen/_reference.py keeps the original implementation, and CI asserts the fast path matches it to atol=1e-12 across 38 parametrised cases — four grid shapes, three dimensionalities, three seeds, plus the notebook’s own configuration. Worst observed deviation: 2.220e-16, exactly np.finfo(np.float64).eps.

Most refactors delete the code they replace. Keeping it as an executable oracle is what makes rewriting a numerical routine safe rather than merely plausible. A further test asserts the oracle is never imported by shipped code.

What I did not do, and why

  • No GPU or numba backend. At 100×100 this finishes in about two seconds. A CUDA path would be complexity the data doesn’t justify.
  • No REST inference API. A SOM is a batch training job, not an online-inference product. Building /predict would demonstrate familiarity with FastAPI and a misunderstanding of the workload.
  • No CLI or Docker image. Both straightforward; neither was the bottleneck. Time went into the equivalence proof, which is what makes every other claim here trustworthy.
  • somoclu was not benchmarked. The C++/OpenMP implementation would plausibly beat this one at large grids, and that result would have been published had it run — but it doesn’t build on Windows. This is a gap in the comparison, not a favourable omission.

The caveat matters more than the win

MiniSom is not running the same algorithm. It uses asymptotic decay 1/(1+t/(T/2)) rather than the exponential decay this brief specifies, so raw wall-clock across the two isn’t like-for-like. The benchmark normalises on weight updates performed and records the difference in every MiniSom row of the output JSON.

Quantisation error tells the same story from the other direction: identical between the original and this library, as the equivalence proof requires — but different for MiniSom. The two libraries are solving slightly different problems.

Where the wheel wins

scikit-learn has no SOM, so MiniSom is the real comparator — but the thing worth borrowing from scikit-learn isn’t code, it’s the interface. Hyperparameters in __init__, learned state as weights_, fit returning self. This library follows all three without taking the dependency: a 200-line numerical package shouldn’t pull in a large transitive tree to borrow a convention.

For any audience

A map that organises itself

Give it a pile of things it has never seen and no instructions about what they are. It arranges them on a grid so that similar things end up near each other. Nobody tells it what “similar” means — it works that out from the data.

What just happened

Three things repeat, thousands of times:

  1. Find the closest match. For each colour, find the square on the grid that already looks most like it.
  2. Pull that square closer. Nudge it toward the colour — and nudge its neighbours too, less the further away they are.
  3. Narrow the reach, and slow down. Each pass, the neighbourhood shrinks and the nudges get gentler. Early on the map organises broadly; later it refines locally.

Step two is the whole trick. Because neighbours move together, nearby squares stay similar — and the smooth gradient you watched emerge is the consequence. Nobody specified it.

Why this is useful

Colours have three dimensions, so a picture of them is easy. The technique’s value is that it works identically on data with hundreds of dimensions — where no picture is possible and human intuition runs out. It presses that data onto a two-dimensional map you can actually look at.

Customer segmentation
Group customers by behaviour without deciding the categories in advance — the segments emerge from the data.
Fraud and anomaly detection
Transactions landing far from every part of the map are, by construction, unlike anything seen before.
Document clustering
Organise a large body of text by topic without a predefined taxonomy.
Equipment health monitoring
Sensor readings drifting to a new region of the map indicate a machine behaving unlike its own history.

When it’s the wrong tool

An explainer that only sells isn’t an engineering document.

  • When you already know the answer. With labelled data and a specific question, a supervised model will beat this comfortably.
  • When you need a crisp number of groups. A SOM produces a smooth landscape, not tidy clusters. Drawing boundaries on it is a separate judgement call.
  • When the result must be explained to a regulator. “It landed in this region of the map” is a weaker account than an explicit decision rule.
  • When the grid must be enormous. Cost grows with grid area. Beyond roughly a thousand squares a side, this needs different machinery.
